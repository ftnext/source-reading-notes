## 調査上の注意

- `git log --oneline 1.6.0..1.7.0` は 56 コミット。`git diff --stat 1.6.0 1.7.0 -- starlette` は 22 ファイル、+329 / -272 行と小規模。
- 56 コミットのうちリリースノートに載っていないものは、docs の文言修正、CodSpeed ベンチマーク追加・安定化（`#3448`〜`#3455`, `#3462`, `#3464`, `#3469`, `#3524`）、dependabot、開発用依存の更新（`#3509`）、`TestClient` の HTTP メソッドオーバーライド削除（`#3488`）など、利用者に直接影響しないもの。本ノートでは末尾の「リリースノート外の変更」でまとめて触れる。
- `[差分]` はソース差分・PR から確認した事実、`[推測]` は差分から読み取れる範囲での推測。

## 全体の要点

1. **実験的な `OpenTelemetryMiddleware`** が追加（`starlette.middleware.opentelemetry`、`opentelemetry-api` が必要、`starlette[full]` に含まれる）。HTTP サーバスパンを生成し、`excluded_urls` で除外、`tracer_provider` / `meter_provider` を指定可能。API と出力テレメトリはマイナーリリースでも予告なく変わり得る。
2. **`scope["route"]`** でマッチしたルートが取れるようになった（OpenTelemetry の `http.route` 属性算出のために追加された公開仕様）。
3. **HTTP `QUERY` メソッド**を `HTTPEndpoint`、`CORSMiddleware` の `allow_methods=["*"]`、OpenAPI 3.2 以上のスキーマ生成でサポート。
4. **`TestClient` の機能強化**: レスポンストレーラーを `response.extensions["http.response.trailers"]` で取得可能、IPv6 ホストの扱い、AnyIO 4.15 で非推奨になった import の回避。
5. **依存関係の変更（実質的な破壊的変更）**: `anyio>=4.0.0,<5` を要求し AnyIO 3 のサポートを廃止。Python 3.15 をサポート。
6. **`WebSocketDisconnected`（`RuntimeError` のサブクラス）** を、切断済み WebSocket への操作で送出。`RuntimeError` を捕まえている既存コードはそのまま動く。
7. **Cookie の `Partitioned` 属性対応の拡充**: `SessionMiddleware(partitioned=True)`、`Response.delete_cookie(partitioned=...)`（Python 3.14 以上）。
8. **セキュリティ・堅牢性寄りの修正**: 不正な `Host` ヘッダーの一貫した拒否、IPv6 の `Host` 対応、`Vary: Origin` の常時付与、multipart の不正入力で 400、`StaticFiles` への WebSocket 要求の拒否など。
9. **`BaseHTTPMiddleware` でのバックグラウンドタスク実行タイミング修正**: レスポンス送信完了後に実行されるようになった（`Response.background` の本来の意味に一致）。
10. **その他のバグ修正**: `FileResponse` の非 200 ステータスで `Range` を無視、`If-None-Match: *`、`Session` の `popitem()` / `|=` 追跡、`WebSocketEndpoint.decode()` の空ペイロード、`SimpleUser.identity`、非標準ステータスコードの `HTTPException`、デバッグトレースバック生成のスレッド退避。

## 移行時の注意（まとめ）

- **AnyIO 3 を使っている環境は 1.7.0 にアップグレードできない**（`pip` が `anyio>=4` を要求する）。AnyIO 4 では例外グループの扱いが変わるため、AnyIO 3 に依存する他ライブラリとの組み合わせを確認すること。
- `CORSMiddleware` を使っている場合、`Origin` ヘッダーのないレスポンスにも `Vary: Origin` が付くようになる。CDN 等でキャッシュキーが変わり得る（意図された挙動）。
- `TrustedHostMiddleware` / `HTTPSRedirectMiddleware` / `Host` ルートが、不正な `Host` ヘッダーに対して 400 を返す（または非マッチ）ようになった。RFC 3986 に沿わない `Host` を送るクライアントがあれば影響を受ける。
- `HTTPEndpoint` で `query` メソッドを定義していると、`QUERY` リクエストが処理対象になり、`Allow` ヘッダーにも `QUERY` が含まれる。
- `BaseHTTPMiddleware` 配下でバックグラウンドタスクの完了を前提にしたテストを書いていた場合、実行タイミングが「レスポンス送信後」に変わる。
- `TestClient` の `get` / `post` 等のオーバーライドが削除されたが、`httpx.Client` の同名メソッドがそのまま使われるため呼び出し側の変更は不要。

## Added

### 実験的な `OpenTelemetryMiddleware` の追加 (#3438, #3463, #3520, #3574)

- PR: https://github.com/Kludex/starlette/pull/3438 , https://github.com/Kludex/starlette/pull/3463 , https://github.com/Kludex/starlette/pull/3520 , https://github.com/Kludex/starlette/pull/3574 (experimental の明記)
- ソース: https://github.com/Kludex/starlette/blob/1.7.0/starlette/middleware/opentelemetry.py
- ドキュメント: https://github.com/Kludex/starlette/blob/1.7.0/docs/middleware.md

**何が変わったか** `[差分]`

- 新モジュール `starlette/middleware/opentelemetry.py` に `OpenTelemetryMiddleware(app, *, excluded_urls=(), tracer_provider=None, meter_provider=None)` を追加。
- `opentelemetry-api` が import できない場合は `ImportError("The `opentelemetry-api` package is required to use `OpenTelemetryMiddleware`.")` を送出。`pyproject.toml` の `full` extra に `opentelemetry-api` が追加された。
- 動作:
  - `scope["type"] != "http"` のとき（WebSocket・lifespan）は何もしない。
  - `scope["starlette.opentelemetry"]` フラグで、同じリクエストに複数インスタンスが重なっても 1 スパンだけ作る。
  - tracer provider が `NoOpTracerProvider`（未設定）のときはスパンを作らずパススルー。
  - `excluded_urls` はカンマ区切り文字列またはシーケンスの正規表現。完全な URL (`str(URL(scope=scope))`) に `search` でマッチしたら計測しない。
  - `propagate.extract(headers)` で親コンテキストを取り込み、`SpanKind.SERVER` のスパンを HTTP メソッド名で開始。属性は OpenTelemetry セマンティック規約に沿った `http.request.method`, `url.path`, `url.scheme`, `url.query`, `server.address`, `server.port`, `network.protocol.version`, `client.address`, `user_agent.original`。
  - レスポンス開始時に `http.response.status_code` を設定し、5xx なら `error.type` とステータス `ERROR`。アプリが例外を投げたら `error.type` に例外クラス名。
  - 終了時に `scope["route"]`（次項）から `http.route` を求め、スパン名を `"{METHOD} {route_path}"` に更新。`Mount` の場合は `root_path`、それ以外は `route.path_format` を使う。
- `meter_provider` 引数は受け取って保持するだけで、1.7.0 時点ではメトリクスを出力していない `[差分]`。将来のメトリクス対応のための先行追加と考えられる `[推測]`。

**変更前と変更後の挙動**

- 変更前: Starlette 本体にトレーシング機能はなく、`opentelemetry-instrumentation-starlette` / `-asgi` など外部の計装パッケージが必要だった。
- 変更後: `opentelemetry-api` だけあれば Starlette 標準のミドルウェアでサーバスパンを出せる。SDK とエクスポータの設定はアプリ側の責務。

**利用者への影響**

- オプトインの新機能。追加しなければ影響なし。
- experimental のため、マイナーリリースで API・属性名が変わる可能性がある（`#3574` でドキュメント・docstring・リリースノートに明記）。
- Pydantic Logfire のようにグローバルプロバイダを設定するライブラリと組み合わせる例がドキュメントにある。

```python
from starlette.applications import Starlette
from starlette.middleware import Middleware
from starlette.middleware.opentelemetry import OpenTelemetryMiddleware

app = Starlette(
    routes=[...],
    middleware=[Middleware(OpenTelemetryMiddleware, excluded_urls=r"/health$,/readiness$")],
)
```

### マッチしたルートを `scope["route"]` で公開 (#3438)

- PR: https://github.com/Kludex/starlette/pull/3438
- ソース差分: `starlette/routing.py` の `Router.app()`

**何が変わったか** `[差分]`

- `Router` が `Match.FULL` でルートを選んだとき `scope["route"] = route`、`Match.PARTIAL`（405 になるケースなど）で `scope["route"] = partial` を設定するようになった。

**変更前と変更後の挙動**

- 変更前: どのルートにマッチしたかを scope から知る公式の手段はなく、`scope["endpoint"]` や `scope["path_params"]` から推測するしかなかった。
- 変更後: `request.scope["route"]` で `Route` / `Mount` / `Host` などの `BaseRoute` インスタンスが得られる。ネストした `Router`/`Mount` の場合は最も内側で最後にマッチしたルートに上書きされる `[差分]`。

**利用者への影響**

- ミドルウェアやロギングで `route.path_format` をキーにしたメトリクス集計ができる。
- `scope` に新しいキーが増えるだけで既存動作は変わらない。

### `QUERY` HTTP メソッドのサポート (#3489)

- PR: https://github.com/Kludex/starlette/pull/3489
- ソース差分: `starlette/endpoints.py`, `starlette/middleware/cors.py`, `starlette/schemas.py`

**何が変わったか** `[差分]`

- `HTTPEndpoint._allowed_methods` の候補に `"QUERY"` を追加。クラスに `async def query(self, request)` を定義すると `QUERY` リクエストにディスパッチされ、`Allow` ヘッダーにも含まれる。
- `CORSMiddleware.ALL_METHODS` に `"QUERY"` を追加。`allow_methods=["*"]` のときプリフライトの `Access-Control-Allow-Methods` に `QUERY` が含まれる。
- `SchemaGenerator.get_schema()` は `openapi` フィールドのバージョンを正規表現で解釈し、3.2 以上のときだけ `query` メソッドのエンドポイントをスキーマに含める。3.1 以下では `query` を黙ってスキップする。`BaseSchemaGenerator.get_endpoints()` の探索対象メソッドにも `query` が加わった。
- 注意: `Route(methods=["QUERY"])` は以前から任意の文字列を受け付けていたため、関数ベースのルーティングでは以前から動いていた。今回はクラスベース・CORS・スキーマ生成の 3 点が追従した形 `[差分]`。

**利用者への影響**

- `QUERY`（RFC 化が進む、ボディ付きの安全・冪等なメソッド）を使うアプリを Starlette の慣用的な書き方で実装できる。
- `HTTPEndpoint` にたまたま `query` という名前のメソッドを持っていた場合、それが HTTP ハンドラとして扱われるようになる（該当ケースは少ないと思われる `[推測]`）。

### `TestClient` でレスポンストレーラーを取得 (#3563)

- PR: https://github.com/Kludex/starlette/pull/3563
- ソース差分: `starlette/testclient.py` の `_TestClientTransport.handle_request()`
- ドキュメント: https://github.com/Kludex/starlette/blob/1.7.0/docs/testclient.md （「HTTP trailers」節）

**何が変わったか** `[差分]`

- scope の `extensions` に `"http.response.trailers": {}` を宣言し、ASGI HTTP trailers 拡張をサポートしていることをアプリに伝える。
- `http.response.start` の `trailers: True` を見て `trailers_expected` を立て、ボディ完了後に届く `http.response.trailers` メッセージの `headers` を蓄積。`more_trailers` が偽になったらレスポンス完了。
- 結果は `response.extensions["http.response.trailers"]` に `list[tuple[bytes, bytes]]` として格納（順序・重複を保持、`response.headers` とは別）。トレーラーを宣言しないレスポンスにはこのキーは付かない。
- 順序違反（ボディ完了前のトレーラー、宣言なしのトレーラー、ボディ完了後の追加ボディ）は `assert` で検出し、`raise_server_exceptions=True` ならテスト失敗になる。

**変更前と変更後の挙動**

- 変更前: アプリが `http.response.trailers` を送ると、`TestClient` は未知のメッセージ型として扱い、トレーラーは検証できなかった。
- 変更後: 上記の通り取得・検証できる。ただし `TE: trailers` ヘッダーの有無に関わらず常に捕捉し、HTTP/2 フレーミングは模倣しない。

**利用者への影響**

- gRPC-web や Trailer を使う ASGI アプリのテストが書けるようになる。トレーラーを使わないアプリには影響なし。

### `SessionMiddleware` の partitioned cookie 対応 (#3510)

- PR: https://github.com/Kludex/starlette/pull/3510
- ソース差分: `starlette/middleware/sessions.py`

**何が変わったか** `[差分]`

- `SessionMiddleware.__init__` に `partitioned: bool = False` を追加。真なら `security_flags` に `; partitioned` を付与し、セッション Cookie の設定・削除の両方で `Partitioned` 属性が付く。
- `Response.set_cookie` とは異なり、Python バージョンによる制限はない（文字列連結で生成しているため）`[差分]`。

**利用者への影響**

- iframe 埋め込みなどクロスサイト文脈で CHIPS (Cookies Having Independent Partitioned State) を使いたい場合に有効。ドキュメントでは `https_only=True`、クロスサイト埋め込みでは `same_site="none"` の併用を推奨。
- デフォルトは `False` で既存挙動は不変。

### `Response.delete_cookie()` に `partitioned` を追加 (#3376)

- PR: https://github.com/Kludex/starlette/pull/3376
- ソース差分: `starlette/responses.py`

**何が変わったか** `[差分]`

- `delete_cookie(..., partitioned: bool = False)` を追加し、内部で呼ぶ `set_cookie` に引き渡す。`set_cookie` 側の `partitioned` は既存で、Python 3.14 未満では `ValueError` を送出する（`http.cookies` が `partitioned` 属性を知らないため）。

**変更前と変更後の挙動**

- 変更前: `Partitioned` 属性付きで設定した Cookie を `delete_cookie` で消そうとしても属性が付かず、ブラウザが同一 Cookie と見なさず削除できなかった。
- 変更後: `partitioned=True` を渡せば同じ属性で失効させられる。

**利用者への影響**

- Python 3.14 以上で partitioned cookie を使っている利用者向け。それ以外は無関係。

### `TrustedHostMiddleware` と `TestClient` の IPv6 ホスト対応 (#3471)

- PR: https://github.com/Kludex/starlette/pull/3471
- ソース差分: `starlette/middleware/trustedhost.py`, `starlette/testclient.py`, `starlette/routing.py`, `starlette/_utils.py`

**何が変わったか** `[差分]`

- `TrustedHostMiddleware` は従来 `host.split(":")[0]` でポートを落としていたため、`[::1]:8000` のような IPv6 は `[` だけになりマッチできなかった。新設の `parse_host_header()`（後述 #3472）を使い、ブラケット付きの `[::1]` をホストとして扱う。`allowed_hosts=["[::1]"]` のようにブラケット付きで指定する。
- `Host` ルートの `compile_path()` も末尾が `]` なら `rsplit(":", 1)` をしない。
- `TestClient` は `request.url.netloc` を `:` で分割していたのをやめ、`request.url.raw_host` / `request.url.port` を使い、`Host` ヘッダーには `request.url.netloc` をそのまま使う。これにより `TestClient(app, base_url="http://[::1]")` が正しい `Host` と `scope["server"]` を生成する。

**利用者への影響**

- IPv6 アドレスで直接アクセスされるサービスで `TrustedHostMiddleware` が使えるようになる。ホスト名やIPv4 のみの環境では挙動は変わらない。

## Changed

### `anyio>=4.0.0,<5` を要求（AnyIO 3 サポート廃止） (#3512)

- PR: https://github.com/Kludex/starlette/pull/3512
- ソース差分: `pyproject.toml`, `starlette/_utils.py`, `starlette/testclient.py`, `starlette/middleware/base.py`

**何が変わったか** `[差分]`

- 依存を `anyio>=3.6.2,<5` から `anyio>=4.0.0,<5` に変更。
- `_utils.py` の Python 3.11 未満向け `BaseExceptionGroup` フォールバック（`exceptiongroup` が無ければダミークラスを定義）を削除し、`from exceptiongroup import BaseExceptionGroup` を直接 import。AnyIO 4 は `exceptiongroup` を必須依存に持つため安全。
- `anyio.create_memory_object_stream[Message]()` のような AnyIO 4 のジェネリック構文に統一（`base.py`, `testclient.py`）。

**利用者への影響**

- **破壊的変更（依存関係）**: AnyIO 3 系に固定された環境ではインストールできない。AnyIO 4 は 2023 年 8 月リリースで、Trio / httpx など主要ライブラリは既に対応済みなので、実際に影響を受ける環境は限定的と思われる `[推測]`。

### 切断済み WebSocket 操作で `WebSocketDisconnected` を送出 (#2767)

- PR: https://github.com/Kludex/starlette/pull/2767
- ソース差分: `starlette/websockets.py`

**何が変わったか** `[差分]`

- `class WebSocketDisconnected(RuntimeError)` を新設。
- 以下の箇所で送出する例外を `RuntimeError` から `WebSocketDisconnected` に変更:
  - `receive()`: 切断メッセージ受信後の再呼び出し（`'Cannot call "receive" once a disconnect message has been received.'`）
  - `send()`: close 送信後の再呼び出し
  - `receive_text()` / `receive_bytes()` / `receive_json()`: `accept()` 前や切断後（`'WebSocket is not connected. Need to call "accept" first.'`）
- `receive_json()` の `mode` 引数不正など、接続状態と無関係な `RuntimeError` はそのまま。
- 既存の `WebSocketDisconnect(Exception)`（クライアントから切断メッセージが届いたことを表す）とは別物なので名前の混同に注意。

**変更前と変更後の挙動**

- 変更前: 汎用 `RuntimeError` しか投げられず、`except RuntimeError` で他のプログラミングエラーと区別できなかった。
- 変更後: `except WebSocketDisconnected` で「切断済みソケットへの操作」だけを捕まえられる。`RuntimeError` サブクラスなので既存の `except RuntimeError` は引き続き動作する。

**利用者への影響**

- 後方互換。新しい例外型で意図を明確にできる。

### `CORSMiddleware` の設定型注釈を `Collection[str]` に (#3518)

- PR: https://github.com/Kludex/starlette/pull/3518
- ソース差分: `starlette/middleware/cors.py`

**何が変わったか** `[差分]`

- `allow_origins`, `allow_methods`, `allow_headers`, `expose_headers` の型注釈を `Sequence[str]` から `Collection[str]` に変更。実装は `in` と `", ".join()` しか使っておらず、以前から `set` / `frozenset` は実行時に動いていた。

**利用者への影響**

- `allow_origins={"https://a.example", "https://b.example"}` のように set を渡しても mypy / pyright が警告しなくなる。実行時の挙動は不変。

## Fixed

### `BaseHTTPMiddleware` 使用時にバックグラウンドタスクをレスポンス送信後に実行 (#3476)

- PR: https://github.com/Kludex/starlette/pull/3476
- ソース差分: `starlette/middleware/base.py` の `call_next()` 内 `body_stream()`

**何が変わったか** `[差分]`

- `body_stream()` が最後のボディチャンク（`more_body` が偽の `http.response.body`）または `http.response.pathsend` を受け取った時点で `await response_sent.wait()` し、外側のレスポンス送信完了を待ってから内側アプリの `send` を返すようになった。

**変更前と変更後の挙動**

- 変更前: 内側のレスポンス（例: `JSONResponse(..., background=task)`）は自身の最終ボディチャンクをメモリストリームに書き込んだ時点で `__call__` が返り、`background` タスクを実行し始めた。`BaseHTTPMiddleware` がそのチャンクをクライアントへ送る前にタスクが動くため、「レスポンス送信後に実行される」という `BackgroundTask` の契約が崩れていた。
- 変更後: クライアントへの送信が完了してから内側アプリが後処理（バックグラウンドタスク）を実行する。

**利用者への影響**

- バグ修正。ミドルウェアなしの場合と同じタイミングになる。長時間のバックグラウンドタスクがレスポンスの到着を遅らせていたケースが直る。
- テストで「レスポンスが返った時点でバックグラウンドタスクが完了している」ことに依存していた場合は、`TestClient` ではリクエスト完了時にタスクも完了しているので通常は影響しない `[推測]`。

### 不正な multipart 入力で 400 を返す (#3492)

- PR: https://github.com/Kludex/starlette/pull/3492

### CORS: 全レスポンスに `Vary: Origin`、プリフライトは入力ヘッダー全てで `Vary` (#3516, #3517)

- PR: https://github.com/Kludex/starlette/pull/3516 , https://github.com/Kludex/starlette/pull/3517
- ソース差分: `starlette/middleware/cors.py`

**何が変わったか** `[差分]`

- `#3516`: `Origin` ヘッダーの無いリクエストも `send_response` 経由で処理するようになり、`Access-Control-*` ヘッダーは付けないが `Vary: Origin` を付ける。許可されない Origin のレスポンスにも `Vary: Origin` を付ける（従来は `allow_explicit_origin` を通る場合のみ）。
- `#3517`: プリフライト応答の `Vary` を固定で `Origin, Access-Control-Request-Method, Access-Control-Request-Headers, Access-Control-Request-Private-Network` にした（以前は明示 Origin のときだけ `Vary: Origin`）。
- `MutableHeaders.add_vary_header()` の呼び出しをやめ、`headers.getlist("Vary")` と結合して `Vary` を再設定する方式に変更。

**変更前と変更後の挙動**

- 変更前: `Origin` なしのレスポンスは `Vary` なしで返るため、共有キャッシュがそれをキャッシュし、その後 CORS リクエストが来ても `Access-Control-Allow-Origin` の無いレスポンスが返され得た（キャッシュポイズニングの一種）。プリフライトも同様にメソッドやヘッダーが異なるリクエストで誤ったキャッシュが返り得た。
- 変更後: キャッシュはリクエストの `Origin` 等ごとに別エントリを持つ。

**利用者への影響**

- 正しい HTTP キャッシュ挙動になる修正。CDN のキャッシュヒット率が下がる可能性はあるが、正確性のための意図された変更。
- ミドルウェアが付与する `Vary` を前提にしたテストは更新が必要。

### 不正な `Host` ヘッダーと IPv6 authority の一貫した処理 (#3472)

- PR: https://github.com/Kludex/starlette/pull/3472
- ソース差分: `starlette/_utils.py`（`parse_host_header`, `ParsedHost`, `_HOST_RE`）, `starlette/datastructures.py`, `starlette/routing.py`, `starlette/middleware/trustedhost.py`, `starlette/middleware/httpsredirect.py`

**何が変わったか** `[差分]`

- `URL.__init__` 内にあった `_HOST_RE` を `_utils.py` へ移し、RFC 3986 の `reg-name` / `IP-literal`（IPv6 と IPvFuture）/ ポート を受理する正規表現に拡張。`parse_host_header()` は不正なら `None`、正しければ `ParsedHost(host, port)` を返し、IPv6 は `ipaddress.IPv6Address` で妥当性を検証。
- `URL(scope=scope)`: `Host` が不正、または `ParsedHost.is_valid_port` が偽（65535 超のポート等）なら `Host` を無視して `scope["server"]` にフォールバック。`scope["server"]` の host が生の IPv6 の場合は `[...]` で括る。
- `Host.matches()`: 不正な `Host` は `Match.NONE`。
- `TrustedHostMiddleware`: 不正な `Host` は 400 `Invalid host header`。
- `HTTPSRedirectMiddleware`: `URL(scope=scope).netloc` が空（`Host` も `server` も使えない）なら 400 を返す（以前は `https:///path` のような不正 URL にリダイレクトしていた）。

**利用者への影響**

- `Host` インジェクション（パスや `@` を含む `Host` で URL 生成を狂わせる攻撃）に対する防御が各所で一貫する。
- IPv6 リテラルの `Host` を送るクライアント（`curl http://[::1]:8000/` 等）が正しく処理される。
- 準拠しない `Host` を送るクライアントは 400 を受ける可能性がある。

### `WebSocketEndpoint.decode()` で空・欠落ペイロードを処理 (#3372)
