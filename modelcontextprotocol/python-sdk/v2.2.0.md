## 全体の要点

リリースノート冒頭に "A few defaults changed in this release" とある通り、**デフォルト挙動の変更が 3 件**あり、2.x でサーバー/クライアントを運用している場合は要確認。

1. **HTTP クライアントのリダイレクト追従が同一オリジン内に限定**（#3397, #3450）。`Client("https://...")` / `streamable_http_client` / `sse_client` は、同一 scheme・host・port（または同一ホストでの http→https 昇格）へのリダイレクトだけを追う。それ以外へのリダイレクトは追わず、Streamable HTTP では `MCPError`、SSE では `httpx2.HTTPStatusError` になる。渡した `httpx2.AsyncClient` の `follow_redirects` 設定は MCP リクエストには使われなくなった。
2. **アイドルな Streamable HTTP セッション（レガシー ≤2025-11-25 仕様の接続）が 30 分で期限切れ、同時セッション数の上限が 10,000**（#3395）。SDK の `Client` のように GET ストリームを開き続けるクライアント、ステートレスサーバー、2026-07-28 接続には影響しない。`session_idle_timeout=None, max_sessions=None` で無効化可。
3. **OAuth クライアントがレガシー経路（Protected Resource Metadata なし）でも認可サーバー metadata の `issuer` を検証**（#3398）。不一致は `OAuthFlowError`。`insufficient_scope` 以外の 403 は再試行せず呼び出し元へ返す。PRM 取得が 5xx/429 で失敗したらレガシー経路にフォールバックせず停止。
4. **`MCPDeprecationWarning` が 2 つ追加**（#3435, #3447）。`ClientCredentialsOAuthProvider` / `PrivateKeyJWTOAuthProvider` の `issuer=` 省略と、`AuthSettings(resource_server_url=...)` での `validate_token_resource` 未指定。2.x では挙動は変わらないが、テストで警告をエラー扱いにしている場合は影響あり。
5. **新規 API**: `AuthSettings.validate_token_resource`（#3447）、`ClientCredentialsOAuthProvider` / `PrivateKeyJWTOAuthProvider` の `issuer=`（#3398）、Streamable HTTP サーバー入口の `session_idle_timeout=` / `max_sessions=`（#3395）。
6. **バグ修正**: クライアントの DELETE でセッションが即時解放される・拒否された初回リクエストがセッションを残さない（#3395; issues #2455, #3228, #3300）、ツール `outputSchema` の `$ref` をスキーマ文書内だけで解決（#3394）。
7. **内部変更**: 内部の per-version 型バリデータの `RootModel` ラッパーを型エイリアス + `TypeAdapter` に置換（#3470）。ワイヤフォーマットは不変。ドキュメント再構成（#3443）、翻訳更新（#3458）、CI/ワークフロー整備（#3378, #3424, #3445, #3446）、依存更新（#3285, #3449）、conformance 用サンプル拡充（#3442）。

変更の分類:

| 分類 | 項目 |
|---|---|
| 挙動変更（実質的に破壊的） | #3397/#3450 リダイレクト制限、#3395 セッション期限・上限、#3398 issuer 検証・403 の扱い・PRM 5xx/429 時の停止 |
| 非推奨化 | `issuer=` 省略（#3435）、`resource_server_url` あり + `validate_token_resource` 未指定（#3447） |
| 新機能 | `validate_token_resource`、`issuer=`、`session_idle_timeout=` / `max_sessions=` |
| バグ修正 | #3395 のセッション解放まわり、#3394 `$ref` 解決、#3450 userinfo 付き URL の相対リダイレクト |
| 内部変更（利用者に直接影響なし） | #3470（一部例外あり）、#3443、#3458、#3459、#3378、#3424、#3445、#3446、#3285、#3449、#3442 |

リリースノートの **Known gaps**: tasks 拡張（SEP-2663）、DPoP（SEP-1932）、jwt-bearer グラントは未実装で、[ROADMAP.md](https://github.com/modelcontextprotocol/python-sdk/blob/main/ROADMAP.md) が追跡している。

## 各変更項目の解説

### 1. HTTP クライアントのリダイレクトを MCP エンドポイントのオリジン内だけ追従する【挙動変更】

- PR: https://github.com/modelcontextprotocol/python-sdk/pull/3397 （v1.x バックポート: #3448）
- コミット: https://github.com/modelcontextprotocol/python-sdk/commit/c6762e821c527925f0b617db216d00fbd1d0bf99
- 追加修正 PR: https://github.com/modelcontextprotocol/python-sdk/pull/3450 / コミット https://github.com/modelcontextprotocol/python-sdk/commit/9771e6b59c775ecb2584849d389ce9efba23a541
- 主な変更ファイル: `src/mcp/shared/_httpx_utils.py`、`src/mcp/client/streamable_http.py`、`src/mcp/client/sse.py`、`src/mcp/client/auth/oauth2.py`、`src/mcp/client/auth/utils.py`、`src/mcp/client/auth/extensions/identity_assertion.py`、`docs/client/transports.md`、`docs/run/deploy.md`、`docs/migration.md`

**何が変わったか** `[差分]`

- `create_mcp_http_client()` が `follow_redirects=True` を設定しなくなった（httpx2 のデフォルト = 追従しない）。
- `_httpx_utils` に `stream_within_origin` / `request_within_origin` / `sse_within_origin` / `next_request_within_origin` / `redirect_location` / `redirect_note` / `RedirectAwareAuth` が追加された。トランスポートは `client.send(request, stream=True, follow_redirects=False)` を自前でループし、次の条件をすべて満たすリダイレクトだけを `client.max_redirects` 回まで追う:
  - httpx2 が `response.next_request` を構築した（Location 付きのリダイレクト）
  - **メソッドが保たれる**（POST は 307/308 のみ。301/302/303 は httpx2 が body なしの GET に変えるので追わない。GET ストリームは任意のリダイレクト可）
  - `_within_origin`: 送信 URL と同じ `(scheme, host, port)`、または同一ホスト・デフォルトポートでの `http` → `https` 昇格
  - Location が新たに userinfo（`user:pass@`）を持ち込まない（#3450 で「送信 URL と同じ userinfo なら可」に緩和）
- 追わなかったリダイレクトはリダイレクト応答そのものが呼び出し側に返り、`_unfollowed_redirect()` が理由文を組み立てる。https → http への降格は専用メッセージ（TLS 終端プロキシの誤設定を疑う旨）。
- Streamable HTTP クライアント: POST 時は該当 JSON-RPC リクエストを `_resolve_abandoned_request(..., code=INVALID_REQUEST)` でエラー解決するため、呼び出し側には `MCPError` が返り**セッション自体は使い続けられる**。GET ストリームは `logger.warning` を出して開かずに終了（再試行しても同じ結果のため）。
- SSE クライアント: `sse_within_origin` 経由になり、追わないリダイレクトは接続時の `httpx2.HTTPStatusError` になる。
- OAuth プロバイダ（`OAuthClientProvider`、`IdentityAssertionOAuthProvider` 等）は `RedirectAwareAuth` を継承し、metadata 取得・登録・トークン要求などフロー中の自前リクエストにも同じ規則を適用（上限 `_AUTH_REDIRECT_LIMIT = 5`）。

**変更前 / 変更後**

- 前: デフォルトクライアントは `follow_redirects=True` で、別ホストを含む任意のリダイレクトを httpx2 が追従していた。利用者が `httpx2.AsyncClient` を渡す場合は `follow_redirects=True` を自分で付ける必要があった（移行ガイドにも記載）。
- 後: 追従可否は渡したクライアントの `follow_redirects` 設定と無関係に SDK が決める。末尾スラッシュの 307/308 は追う。別オリジンは追わず失敗する。

**利用者への影響**

- 別ホストへリダイレクトする構成（例: `https://api.example.com/mcp` → `https://mcp.example.com/mcp`）は動かなくなる。**エラーメッセージが示す最終 URL をエンドポイントとして設定する**必要がある。
- TLS 終端プロキシの背後で uvicorn が `http://…/mcp/` へリダイレクトしている場合、`Redirect to http://… not followed: it would downgrade this HTTPS endpoint to plain HTTP` で失敗する。サーバー側で `uvicorn --proxy-headers --forwarded-allow-ips=...` を付けるのが本来の修正（`docs/run/deploy.md` に新セクション「Behind a TLS-terminating proxy」）。暫定策はスラッシュ付きの正確な URL を設定すること。
- 自前の `httpx2.AsyncClient` に `follow_redirects=True` を付ける必要がなくなった（ドキュメント・サンプルから削除）。付けたままでも MCP リクエストには効かない。
- `[推測]` セキュリティ動機の変更（ヘッダーや認証情報が設定したエンドポイント以外へ送られないようにする）。PR 本文の詳細は未確認。

**#3450 の追加修正** `[差分][PR]`: `http://user:pass@host/mcp` のように userinfo 付きの URL を設定した場合、相対 `Location: /mcp/` を結合した次リクエストの URL が元の userinfo を引き継ぐため、#3397 の「userinfo があれば追わない」判定で通常の末尾スラッシュリダイレクトまで拒否されていた。「リダイレクト自身が新たに持ち込む userinfo のみ拒否」に修正。v1.30.0（#3448）にはこの修正が最初から含まれている。

### 2. アイドルな Streamable HTTP セッションの期限切れと同時セッション数の上限【挙動変更 + 新機能 + バグ修正】

- PR: https://github.com/modelcontextprotocol/python-sdk/pull/3395 （v1.x バックポート: #3426。Fixes #2455, #3228, #3300）
- コミット: https://github.com/modelcontextprotocol/python-sdk/commit/d2290ca3434731b68ea3e2270bc06a6e6575931b
- 主な変更ファイル: `src/mcp/server/streamable_http_manager.py`、`src/mcp/server/streamable_http.py`、`src/mcp/server/mcpserver/server.py`、`src/mcp/server/lowlevel/server.py`、`docs/run/legacy-clients.md`（新セクション「Session lifetime and limits」）、`docs/run/index.md`、`docs/troubleshooting.md`

**何が変わったか** `[差分]`

- `StreamableHTTPSessionManager.__init__` の `session_idle_timeout` デフォルトが `None` → `DEFAULT_SESSION_IDLE_TIMEOUT = 30 * 60`（1800 秒）に。新引数 `max_sessions: int | None = DEFAULT_MAX_SESSIONS`（`10_000`）を追加。両者は `MCPServer.run(transport="streamable-http", ...)`、`MCPServer.streamable_http_app()`、`run_streamable_http_async()`、`Server.streamable_http_app()` からも渡せる。
- 検証: `session_idle_timeout` は正の有限値（`math.inf` 不可）、`max_sessions` は正の整数または `None`。v2.1.1 にあった「stateless と `session_idle_timeout` の併用で `RuntimeError`」は削除され、stateless では単に無視される。
- アイドル判定の主体がマネージャからトランスポート（`StreamableHTTPServerTransport(idle_timeout=...)`）へ移動。`_requests_in_flight` カウンタで「処理中のリクエスト（開いた GET ストリーム含む）が 1 つでもあれば deadline を `math.inf` に、最後のリクエストが完了した時点でカウントダウン再開」。期限切れ後に届いたリクエストは `terminate()` 後に 404 で応答。
- セッション生成が `_admit_session()`（ロック内で上限チェックと登録のみ）と `_serve_opening_request()`（ロック外で初回リクエストを処理）に分離。初回リクエストの HTTP ステータスを `_send_and_report_status` で観測し、**400 以上なら `_discard_session()` でセッションを破棄**（#3228: `Accept` 不正、JSON 不正、initialize 以外、GET/DELETE などで登録済みセッションとタスクが残っていた問題）。
- クライアントの DELETE 後 `transport.is_terminated` なら即 `_discard_session()`（#3300: 終了済みトランスポートのクリーンアップがスキップされていた）。`_discard_session` はまずテーブルから削除し（以後その ID は 404）、`CancelScope(shield=True)` で `terminate()` を完了させる。
- 上限超過時は `503` + JSON-RPC エラー `code=-32603 (INTERNAL_ERROR)`, `message="Too many open sessions"`。ログは `WARNING` の `Refusing to open a new session: <n> sessions are already open`。期限切れは `INFO` の `Session <id> idle timeout`。
- stateless モードでも、リクエストがキャンセルされてもトランスポートが `terminate()` されるよう `try/finally` + shield に変更。

**変更前 / 変更後**

- 前: `session_idle_timeout` は 1.27 から `StreamableHTTPSessionManager` にあったが `None` がデフォルトで、`MCPServer` / `Server.streamable_http_app()` から設定できなかった（#2455）。DELETE を送らないクライアントのセッションはプロセス終了まで残った。
- 後: 30 分無通信で期限切れ、10,000 セッション上限。既存セッションの追い出し（eviction）はしない。

**利用者への影響**

- **影響を受ける**: レガシー（≤2025-11-25）仕様でステートフル接続し、GET ストリームを開かず、30 分以上間隔を空けてリクエストする独自クライアント。次のリクエストが `404 Session not found` になり、再度 `initialize` が必要。
- **影響を受けない**: SDK の `Client`（GET ストリームを維持）、`stateless_http=True`、2026-07-28 接続（セッションを持たない）。実行中のツール呼び出しはタイムアウトを超えても中断されない。
- 上限は**プロセス単位**。4 ワーカーなら合計 40,000。
- 無効化: `mcp.run(transport="streamable-http", session_idle_timeout=None, max_sessions=None)`。
- `retry_interval` を設定している場合、ポーリング間隔より十分長い `session_idle_timeout` にする（docstring の注意）。

### 3. 認可サーバー metadata の issuer をすべての探索経路で検証する【挙動変更 + 新機能】

- PR: https://github.com/modelcontextprotocol/python-sdk/pull/3398 （v1.x バックポート: #3431）
- コミット: https://github.com/modelcontextprotocol/python-sdk/commit/d060b36e1d095ef6e93e07ba5d59bb69b2ad449a
- 主な変更ファイル: `src/mcp/client/auth/oauth2.py`、`src/mcp/client/auth/utils.py`、`src/mcp/client/auth/extensions/client_credentials.py`、`docs/client/oauth-clients.md`、`docs/migration.md`

**何が変わったか** `[差分]`

- `OAuthClientProvider._expected_issuer()` を追加: PRM が `authorization_servers` を返した場合はその URL、**PRM がないレガシー経路では MCP サーバー自身のオリジン `scheme://authority`**（2025-03-26 仕様の well-known URL の元になる値）を期待 issuer とする。`_origin_issuer()` は `AnyHttpUrl(url_preserve_empty_path=True)` で `OAuthMetadata.issuer` と同じ表記（ホスト小文字化、デフォルトポート省略）に正規化。
- 取得した ASM に対し、経路を問わず `validate_metadata_issuer(asm, expected_issuer)` を実行。レガシー経路ではルート issuer の末尾スラッシュ有無（`https://host` と `https://host/`）は同一視（`issuers_match()` 新設）。不一致は `OAuthFlowError: Authorization server metadata issuer mismatch`。
- SEP-2352 の「保存済みクライアント資格情報は登録した issuer に束縛」判定を、metadata 取得前に `expected_issuer` で一度だけ行う形に整理（従来はレガシー経路で ASM 取得後に再評価していた）。
- **PRM 取得で 5xx または 429 が返り、いずれの探索 URL でも PRM が得られなかった場合**、`OAuthFlowError: Protected resource metadata request failed: HTTP <status>` で停止（従来はレガシー経路へフォールバック）。404 等は従来通りフォールバック。
- **403 の扱い**: `WWW-Authenticate` の `error="insufficient_scope"` のときだけ step-up（スコープ拡張して再認可）する。それ以外の 403 は再試行せず呼び出し元へ返す（従来は `_add_auth_header` して 1 回再送していた）。step-up 時、metadata をまだ持っていなければ（ストレージからトークンを復元した直後など）探索を先に行う。`_validate_response_for_step_up`（`utils.py`）の対象ステータスが `401` のみ → `(401, 403)` に。
- `ClientCredentialsOAuthProvider` / `PrivateKeyJWTOAuthProvider` に `issuer: str | None = None` 引数を追加。指定時は http(s) URL であることを検証し、PRM の `authorization_servers` から一致するものを優先選択（`_preferred_authorization_server`）、トークン要求前に `_require_metadata_for_configured_issuer` で「発見した metadata の issuer が設定値と一致」を要求。不一致なら metadata とトークンを破棄して `OAuthFlowError`。

**変更前 / 変更後**

- 前: issuer 検証は PRM 経路のみ（2.0 から）。レガシー経路では ASM の issuer を検証せず受け入れていた。
- 後: レガシー経路でも「MCP サーバーのオリジン = issuer」でなければ拒否。

**利用者への影響**

- PRM を公開しない古い MCP サーバーで、認可サーバー metadata の `issuer` が MCP サーバーのオリジンと異なる（別ホスト、パス付き等）場合、クライアントは接続できなくなる。サーバー側で PRM（`/.well-known/oauth-protected-resource`）を公開するのが正攻法。`[推測]` RFC 8414 §3.3 / SEP-2468 準拠のための変更。
- スコープ不足以外の 403 が自動再試行されなくなるため、その 403 に依存した挙動があれば呼び出し元で扱う。
- M2M クライアント（client credentials / private key JWT）は `issuer="https://auth.example.com"` を渡すと、資格情報が意図した認可サーバー以外へ送られない。次項の非推奨化と併せて推奨。

### 4. `issuer` なしでの事前登録 OAuth クライアント構築を非推奨化【非推奨化】

- PR: https://github.com/modelcontextprotocol/python-sdk/pull/3435
- コミット: https://github.com/modelcontextprotocol/python-sdk/commit/979208c1157661eac0151f90974a1f96528003fa
- 変更ファイル: `src/mcp/client/auth/extensions/client_credentials.py`、`docs/deprecated.md`、`docs/client/oauth-clients.md`、`examples/stories/oauth_client_credentials/`

**何が変わったか** `[差分]`

`_checked_issuer(None)` が `MCPDeprecationWarning`（`stacklevel=3`）を出すようになった:

> Omitting `issuer` is deprecated and it will be required in 3.0. Without it, the MCP server decides which authorization server receives this client's credentials; pass issuer=<your authorization server's issuer URL> so they are only ever sent there.

`docs/deprecated.md` の「Deprecated SDK helpers」表に追加（従来は `FuncMetadata.call_fn_with_arg_validation()` のみ）。

**利用者への影響**

- 2.x では警告のみで挙動不変。3.0 で `issuer=` が必須になる予定。
- pytest の `filterwarnings = ["error"]` などで警告をエラーにしている場合は失敗するので、`issuer=` を渡す。
- v1.30.0（#3431）でも同じ警告が追加されている。

### 5. `AuthSettings.validate_token_resource` で bearer トークンの resource を検査【新機能 + 非推奨化】

- PR: https://github.com/modelcontextprotocol/python-sdk/pull/3447 （v1.x バックポート: #3451）
- コミット: https://github.com/modelcontextprotocol/python-sdk/commit/0c9136841ff092987a20700ff9c2c9789bda2f40
- 主な変更ファイル: `src/mcp/server/auth/settings.py`、`src/mcp/server/auth/middleware/bearer_auth.py`、`src/mcp/server/auth/provider.py`、`src/mcp/server/mcpserver/server.py`、`src/mcp/server/lowlevel/server.py`、`docs/run/authorization.md`、`docs/deprecated.md`

**何が変わったか** `[差分]`

- `AuthSettings` に `validate_token_resource: bool | None = None` を追加。`model_validator(mode="after")` で
  - `True` かつ `resource_server_url is None` → `ValueError("validate_token_resource requires resource_server_url")`
  - `None` かつ `resource_server_url` あり → `MCPDeprecationWarning`（「3.0 では `True` がデフォルトになる」）
- `BearerAuthBackend.__init__(token_verifier, *, resource_server_url: AnyHttpUrl | None = None)` を追加。`resource_server_url` が与えられると、`TokenVerifier.verify_token()` が返した `AccessToken.resource` を URL として比較（大文字小文字・デフォルトポート表記は同一視、末尾スラッシュは無視）し、一致しないトークンは `logger.warning` を出して拒否（未認証扱い）。
- `MCPServer` / `Server.streamable_http_app()` は `auth.validate_token_resource` が真のときだけ `resource_server_url` を `BearerAuthBackend` に渡す。
- `AccessToken.resource` の docstring 更新: RFC 8707 resource indicator / `aud`。`aud` がリストなら `resource_server_url` に等しい要素を入れる。`TokenVerifier.verify_token` の docstring に、`validate_token_resource` を使わない場合は verifier 自身が audience を検証する責務がある旨を明記。
- 公式サンプル（`docs_src/authorization/`、`examples/servers/simple-auth`、`examples/stories/*`）が `validate_token_resource=True` と `AccessToken(resource=...)` を設定するよう更新。

**変更前 / 変更後**

- 前: SDK は `AccessToken.resource` を一切検査せず、audience 検証は verifier 実装者の責任だった。
- 後: `validate_token_resource=True` で SDK 側が resource 一致を強制できる。未指定は従来通り（`False` 相当）だが警告が出る。

**利用者への影響**

- `AuthSettings(resource_server_url=...)` を使っている全サーバーで `MCPDeprecationWarning` が出る。`True` か `False` を明示する。
  - 認可サーバーがクライアントの `resource` パラメータをトークンに束縛する（MCP クライアントは常に送る）なら `True`。`resource_server_url` はクライアントが接続する正確な URL にする。
  - Auth0 の API identifier や Entra のアプリ ID のように独自 audience を使うなら `False` にし、verifier で `aud` を検査して不一致は `None` を返す。
- `True` にする場合、自作 `TokenVerifier` が `AccessToken.resource` を埋めていないとすべてのトークンが拒否される。

### 6. ツール出力スキーマの `$ref` をスキーマ文書内だけで解決する【バグ修正】

- PR: https://github.com/modelcontextprotocol/python-sdk/pull/3394 （v1.x バックポート: #3396）
- コミット: https://github.com/modelcontextprotocol/python-sdk/commit/6705402e246dc4eb1fcdf4d9902b78d3c9c36e1b
- 変更ファイル: `src/mcp/client/session.py`、`tests/client/test_output_schema_validation.py`

**何が変わったか** `[差分]`

`ClientSession` の出力スキーマ検証で、バリデータを `validator_cls(output_schema, registry=Registry())` と**明示的に空の `referencing.Registry`** 付きで構築。`best_match()` 実行時の `referencing.exceptions.Unresolvable` を捕捉し `RuntimeError(f"Invalid schema for tool {name}: {e}")` に変換。従来あった「typeshed のスタブでは `registry` が必須扱いのため `cast` する」回避策は不要になり削除。

**変更前 / 変更後**

- 前: `$ref` の解決は jsonschema のデフォルトに委ねられ、文書外への参照が解決を試みられる余地があった。未解決の `$ref` は `referencing` の例外がそのまま漏れていた。
- 後: `$ref` は文書内（`#/$defs/...`、`$anchor`、埋め込み `$id`）と同梱メタスキーマだけで解決。それ以外や dangling `$ref` は `RuntimeError`。MCP 仕様の `$ref` resolution 節に準拠。

**利用者への影響**

- 自己完結したスキーマのツールには影響なし。外部 URI への `$ref` を返すサーバーはクライアント側で `RuntimeError: Invalid schema for tool ...` になる。
- `referencing` は `pyproject.toml` に直接依存として宣言されていない（`jsonschema>=4.20.0` 経由の推移的依存）`[差分]`。

## 移行チェックリスト（2.1.x → 2.2.0）

1. クライアントが別オリジンへリダイレクトされる構成なら、最終 URL をエンドポイントに設定する。TLS 終端プロキシ背後のサーバーは `uvicorn --proxy-headers --forwarded-allow-ips=...`。
2. 自前 `httpx2.AsyncClient` の `follow_redirects=True` は不要（残しても無害）。
3. レガシー仕様でステートフル接続し GET ストリームを開かない独自クライアントは、`404 Session not found` で再 `initialize` するか、サーバー側で `session_idle_timeout` を調整。
4. 1 プロセスで 10,000 超のステートフルセッションを扱うなら `max_sessions` を上げる。
5. PRM を公開していない MCP サーバーで、認可サーバーの `issuer` が MCP サーバーのオリジンと異なる場合は PRM を公開する。
6. `ClientCredentialsOAuthProvider` / `PrivateKeyJWTOAuthProvider` に `issuer=` を渡す。
7. `AuthSettings(resource_server_url=...)` に `validate_token_resource=True/False` を明示し、`True` なら `TokenVerifier` が `AccessToken.resource` を返すようにする。
8. `FuncMetadata.output_model` や `mcp.server.auth.handlers.authorize.AnyUrlModel` を直接使っている内部依存コードは修正。
