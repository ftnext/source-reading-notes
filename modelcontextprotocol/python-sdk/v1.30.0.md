## 全体の要点

1. **デフォルト挙動が変わる変更が 3 つ**あり、1.x でサーバー/クライアントを運用している場合は要確認。
   - HTTP クライアントのリダイレクト追従が**同一オリジン内のみ**に制限される（#3448）。別ホストへの 302 等は `httpx.HTTPStatusError` で失敗。
   - Streamable HTTP のステートフルセッションが**30 分無通信で期限切れ**、同時セッション数は **10,000 件が上限**になる（#3426）。
   - OAuth クライアントが認可サーバー metadata の **`issuer` を検証**し、不一致なら `OAuthFlowError`（#3431）。
2. **`DeprecationWarning` が 2 つ追加**（#3431, #3451）。1.x では挙動は変わらないが、テストで警告をエラー扱いにしている場合は影響あり。
3. **新規 API**: `AuthSettings.validate_token_resource`、`ClientCredentialsOAuthProvider` / `PrivateKeyJWTOAuthProvider` の `issuer=`、`FastMCP(session_idle_timeout=, max_sessions=)`。
4. **バグ修正**: ツール出力スキーマ検証で `$ref` がスキーマ文書外へ解決されないようにする（#3396）。

## 各変更項目の解説

### 1. ツール出力スキーマの `$ref` をスキーマ文書内だけで解決する【バグ修正】

- PR: https://github.com/modelcontextprotocol/python-sdk/pull/3396 （main 側は #3394）
- コミット: https://github.com/modelcontextprotocol/python-sdk/commit/5ebdfed4060d8e5b11b8e2348f86bad4d1fb8836
- 変更ファイル: `src/mcp/client/session.py`（`ClientSession._validate_tool_result`）、`tests/client/test_output_schema_validation.py`

**何が変わったか** `[差分]`

`call_tool` の結果を `outputSchema` で検証する際、`jsonschema.validate(..., registry=Registry())` と**明示的に空の `referencing.Registry`** を渡すようになった。加えて `referencing.exceptions.Unresolvable` を捕捉し、`RuntimeError(f"Invalid schema for tool {name}: {e}")` に変換する。

```python
registry: Registry[Any] = Registry()
try:
    validate(result.structuredContent, output_schema, registry=registry)
except Unresolvable as e:
    raise RuntimeError(f"Invalid schema for tool {name}: {e}") from e
```

**変更前 / 変更後**

- 前: `$ref` の解決は jsonschema のデフォルトに委ねられていた。文書外の `$ref` は jsonschema のデフォルト解決に従う（`[推測]` 環境によっては外部参照の取得を試みる余地があった）。未解決の `$ref` は `referencing` 側の例外がそのまま漏れていた。
- 後: `$ref` はスキーマ文書内（`#/$defs/...`, `#/definitions/...`, `$anchor`, 埋め込み `$id`）と jsonschema 同梱のメタスキーマ URI だけで解決される。それ以外に解決が及ぶ場合、および文書内の dangling `$ref` は、既存の不正スキーマ時と同じ形の `RuntimeError` になる。MCP 仕様の [`$ref` resolution](https://modelcontextprotocol.io/specification/2026-07-28/basic#ref-resolution) に準拠。

**利用者への影響**

- 通常のツール（自己完結したスキーマ）には影響なし。API 変更なし。
- サーバーが外部 URI への `$ref` を含む `outputSchema` を返している場合、クライアント側で `RuntimeError: Invalid schema for tool ...` になる。スキーマを自己完結にする必要がある。
- レビューコメントで「`referencing` が直接依存に宣言されていない（`jsonschema` 経由の推移的依存）」との指摘があった `[PR]`。差分上、`pyproject.toml` は変更されていない `[差分]`。

### 2. アイドルな Streamable HTTP セッションの期限切れと同時セッション数の上限【挙動変更 + 新機能】

- PR: https://github.com/modelcontextprotocol/python-sdk/pull/3426 （main 側は #3395。#3059 を supersede）
- コミット: https://github.com/modelcontextprotocol/python-sdk/commit/92120b4b64ddc69a8d3f97a67e5c3ba4fb5ed3c5
- 変更ファイル: `src/mcp/server/streamable_http_manager.py`、`src/mcp/server/streamable_http.py`、`src/mcp/server/fastmcp/server.py`、`docs/server.md`

**何が変わったか** `[差分]`

- `StreamableHTTPSessionManager` に定数 `DEFAULT_SESSION_IDLE_TIMEOUT = 30 * 60` と `DEFAULT_MAX_SESSIONS = 10_000` が追加され、`__all__` にも公開された。
- `session_idle_timeout` のデフォルトが `None` → `1800` に変更。`max_sessions: int | None = 10_000` を新設。
- `FastMCP(...)` のコンストラクタと `Settings` に `session_idle_timeout` / `max_sessions` が追加され、`streamable_http_app()` 生成時にマネージャへ渡される。
- アイドル判定の実装が変わった。旧実装はマネージャ側で「HTTP リクエストが来るたびに deadline を延長」していたが、新実装では `StreamableHTTPServerTransport` が `idle_timeout` を受け取り、**in-flight のリクエスト数**（開いている GET ストリームを含む）を数え、0 になった時点からカウントダウンを始める。処理中のリクエストがある間は `deadline = math.inf`。
- セッション上限の判定は `_admit_session()` でロック下で行い、上限到達時は `503` + JSON-RPC エラー（code `-32603` = `INTERNAL_ERROR`、message `Too many open sessions`）を返す。ログは WARNING `Refusing to open a new session: N sessions are already open`。
- 付随する整理:
  - クライアントの `DELETE` で終了したセッションを即座にマネージャから削除（旧: サーバータスク終了時）。
  - 初回リクエストが拒否・失敗・キャンセルされたセッションは残さず破棄（`_serve_opening_request`）。
  - ステートレスモードでリクエストがキャンセルされてもトランスポートを `CancelScope(shield=True)` で確実に terminate。
  - バリデーション: `session_idle_timeout` は正の**有限**値（`math.isfinite`）、`max_sessions` は正の整数。ステートレスモードでタイムアウトを指定しても例外にならなくなった（旧: `RuntimeError`）。
  - 1.x 固有の設計として、期限切れ時は `Server.run()` をキャンセルするのではなくセッションを discard する（クライアント `DELETE` と同じ経路）。1.x では `Server.run()` がセッション毎に `lifespan` に入るため、期限切れでも lifespan の teardown が通常終了と同一になる `[PR]`。

**変更前 / 変更後**

- 前: デフォルトではセッションは無期限。`DELETE` を送らないクライアントのセッションはプロセス終了まで残る。`session_idle_timeout` は `StreamableHTTPSessionManager` にはあったが `FastMCP` から設定できなかった。
- 後: 30 分間 in-flight なしのセッションは閉じられ、次のリクエストは `404 Session not found`（再 `initialize` が必要）。同時 10,000 セッション超は `503`。

**利用者への影響**

- **SDK のクライアント（`streamablehttp_client`）は GET ストリームを開いたままにするため影響なし** `[差分][PR]`。影響を受けるのは、GET ストリームを張らずリクエスト間隔が 30 分を超える独自クライアント。
- 30 分を超える長時間のツール呼び出しは中断されない（処理中は in-flight としてカウントされる）。
- 以前の挙動に戻すには:

  ```python
  mcp = FastMCP("My server", session_idle_timeout=None, max_sessions=None)
  ```

- 上限はプロセス単位。ワーカー 4 つなら合計 4 × `max_sessions`。
- `stateless_http=True` ではどちらも無関係。
- `retry_interval` を使っている場合は、アイドルタイムアウトを retry 間隔より十分長くする（docstring の注意）。

### 3. 認可サーバー metadata の `issuer` を全ディスカバリ経路で検証【挙動変更 + 新機能 + 非推奨化】

- PR: https://github.com/modelcontextprotocol/python-sdk/pull/3431 （main 側は #3398, #3435。関連: #2921, #2933, #2936, #2946, #3181 の一部を同梱）
- コミット: https://github.com/modelcontextprotocol/python-sdk/commit/3eed7ce0a6aba76e8d94c4cfb9b266f41935392c
- 変更ファイル: `src/mcp/client/auth/oauth2.py`、`src/mcp/client/auth/utils.py`、`src/mcp/client/auth/extensions/client_credentials.py`、`src/mcp/shared/auth.py`、`.github/actions/conformance/expected-failures.yml`

**何が変わったか** `[差分]`

1. **issuer 検証（RFC 8414 §3.3 / SEP-2468）**: `utils.validate_metadata_issuer(oauth_metadata, expected_issuer)` と `issuers_match(a, b)` を新設。期待 issuer は `OAuthClientProvider._expected_issuer()` で決まり、PRM（Protected Resource Metadata）が広告する認可サーバー URL、PRM のないレガシー経路では**リソースサーバーのオリジン**（`_origin_issuer`）。取得した認可サーバー metadata の `issuer` がこれと一致しなければ `OAuthFlowError("Authorization server metadata issuer mismatch: ... != ...")`。比較は単純文字列比較だが、ルート issuer の末尾スラッシュ有無（`https://a.example` と `https://a.example/`）だけは同一視する。
2. **クライアント登録情報の issuer バインディング（SEP-2352）**: `OAuthClientInformationFull.issuer: str | None` を追加。SDK が登録成功時に「どの認可サーバーに登録したか」を記録する（登録レスポンスの `issuer` フィールドは信頼せず、パース前に削除）。次回以降、期待 issuer と保存済み credentials の issuer が異なれば、`credentials_match_issuer()` により client_info とトークンを破棄して再登録する。CIMD（URL ベースの client_id）は可搬なので常に一致扱い。issuer 未記録（旧バージョンで保存されたもの・事前登録）はバインディングなしとして従来通り。
3. **PRM 取得で 5xx/429 が返った場合はフローを停止**: `OAuthFlowError("Protected resource metadata request failed: HTTP 5xx")`。旧実装はレガシー経路へフォールバックしていた。
4. **403 `insufficient_scope`（スコープ step-up）の統合**: 403 処理が 401 と同じディスカバリ経路に統合され、metadata を保持していない場合（例: トークンをストレージから読み込んだ直後）はまずディスカバリを行う。`extract_resource_metadata_from_www_auth` も 403 を受け付けるようになった。
5. **`issuer=` キーワード**: `ClientCredentialsOAuthProvider` と `PrivateKeyJWTOAuthProvider` に `issuer: str | None = None` を追加。指定時は PRM が複数の認可サーバーを広告していれば issuer に一致するものを優先選択し、トークンリクエストはその issuer の metadata からのみ構築。他の metadata しか無ければ `OAuthFlowError`。http(s) 以外の値は `ValueError`。
6. **非推奨化**: 上記 2 プロバイダで `issuer=` を省略すると `DeprecationWarning`（「3.0 で必須になる」）。1.x では従来通り動作する。

**変更前 / 変更後**

- 前: metadata の `issuer` は一切検証されず、保存済み `client_id`/`client_secret` はリソースサーバーが次に指し示したどの認可サーバーへも送られていた。
- 後: 期待 issuer を先に決め、metadata・credentials をそれに照合する。不一致は拒否または再登録。

**利用者への影響**

- 正しく設定された認可サーバーであれば透過的。ただし **metadata の `issuer` が well-known URL の元 URL と（テナントパス等で）一致しないサーバー**では `OAuthFlowError` になる。conformance harness 0.1.13 の `auth/metadata-var2` / `var3` がまさにこのケースで、`expected-failures.yml` に一時的に登録された `[差分][PR]`。
- M2M プロバイダ利用者は `issuer="https://auth.example.com"` を渡すことを推奨（警告回避 + セキュリティ向上）。
- `OAuthClientInformationFull` を独自の `TokenStorage` でシリアライズしている場合、新フィールド `issuer` が保存対象に増える。
- 1.x では RFC 9207 `iss` 検証や SEP-2350 のスコープ union は含まれない（main との差分） `[PR]`。

### 4. リダイレクトを MCP エンドポイントのオリジン内でのみ追従【挙動変更】

- PR: https://github.com/modelcontextprotocol/python-sdk/pull/3448 （main 側は #3397）
- コミット: https://github.com/modelcontextprotocol/python-sdk/commit/210633572d26db1a0e47b05aa06ba7da9a94cc86
- 変更ファイル: `src/mcp/shared/_httpx_utils.py`、`src/mcp/client/streamable_http.py`、`src/mcp/client/sse.py`、`src/mcp/client/auth/oauth2.py`、`docs/client.md`、`docs/authorization.md`、examples

**何が変わったか** `[差分]`

- `create_mcp_http_client()` が `follow_redirects=True` を設定しなくなった（httpx デフォルトの off）。
- `_httpx_utils` に以下のヘルパーが追加され、トランスポートの全リクエスト（POST / GET ストリーム / DELETE、SSE の POST）がこれを経由する。
  - `next_request_within_origin(response)`: httpx が組んだ次リクエストが「同一 scheme/host/port、または同一ホストでデフォルトポートの http→https」「メソッドが変わらない（POST は 307/308 のみ、GET は任意の 3xx）」「Location に新たな userinfo を含まない」を全て満たす場合のみ返す。
  - `stream_within_origin()` / `request_within_origin()` / `sse_within_origin()`: `follow_redirects=False` で送信し、上記条件を満たすリダイレクトのみ `client.max_redirects` 回まで自前で追従。それ以外はリダイレクトレスポンスをそのまま返す。
  - `RedirectAwareAuth(ABC, httpx.Auth)`: `OAuthClientProvider` の新しい基底クラス。auth フロー内の副リクエスト（metadata 取得・登録・トークン）にも同じ規則を適用（最大 5 回）。従来の `async_auth_flow` は `_auth_flow` にリネームされ、`async_auth_flow` は基底クラスが駆動する。
- 追従されなかったリダイレクトは `httpx.HTTPStatusError` として送出。メッセージは `Redirect to <URL> not followed; use that URL as the endpoint if it is the intended server`。https→http のダウングレードは専用メッセージ（TLS 終端プロキシの設定不備を示唆し、`--proxy-headers` 等を案内）。GET ストリーム側では WARNING ログを出して再試行を止める。エラーメッセージ内の URL からは userinfo・query・fragment を除去する（`redirect_location`）。
- `sse_client` は接続失敗時に receive 側ストリームも `finally` で閉じるようになった（GC 任せだったリソース解放の修正）。
- ドキュメント・サンプルから `follow_redirects=True` を削除。`docs/client.md` に「HTTP redirects」節を追加。

**変更前 / 変更後**

- 前: デフォルトクライアントは**すべてのリダイレクトを追従**（別ホストへもヘッダー・認証・ボディを送っていた）。利用者が渡した `httpx.AsyncClient` は `follow_redirects=True` を設定しない限り末尾スラッシュの 307 ですら追従しなかった。
- 後: どのクライアントを渡しても、同一オリジン内・メソッド維持のリダイレクトだけ追従。`follow_redirects` 設定は MCP リクエストには参照されない。

**利用者への影響**

- `/mcp` → `/mcp/` の末尾スラッシュ 307 は引き続き（むしろ自前クライアントでも設定なしで）動く。
- **別オリジンへリダイレクトするエンドポイント URL を設定していた場合は失敗する**。エラーメッセージが示すリダイレクト先を直接エンドポイントに指定する必要がある。
- POST に対する 301/302/303 は追従されない（メソッドが GET に変わりボディが落ちるため）。
- 1.x にはリクエスト単位の HTTP エラー経路がないため、失敗はタスクグループ内の `httpx.HTTPStatusError` として接続終了になる `[PR]`。
- 1.x は `httpx` / `httpx-sse` のまま（main は `httpx2`）。httpx 0.27.2〜0.28.1 で確認済み `[PR]`。

### 5. `AuthSettings.validate_token_resource` でトークンの resource を検証【新機能 + 非推奨化】

- PR: https://github.com/modelcontextprotocol/python-sdk/pull/3451 （main 側は #3447）
- コミット: https://github.com/modelcontextprotocol/python-sdk/commit/8c2fa6ea9ea15d0ea41d9e8a2a25f41b7b3da4e8
- 変更ファイル: `src/mcp/server/auth/settings.py`、`src/mcp/server/auth/middleware/bearer_auth.py`、`src/mcp/server/auth/provider.py`、`src/mcp/server/fastmcp/server.py`、`docs/authorization.md`、examples

**何が変わったか** `[差分]`

- `AuthSettings.validate_token_resource: bool | None = None` を追加。`model_validator` で
  - `True` かつ `resource_server_url` 未設定 → `ValueError("validate_token_resource requires resource_server_url")`
  - `None` かつ `resource_server_url` 設定あり → `DeprecationWarning`（「3.0 では True がデフォルトになる」）、挙動は `False` と同じ
- `BearerAuthBackend.__init__(token_verifier, *, resource_server_url: AnyHttpUrl | None = None)` にキーワード引数を追加。設定時、`TokenVerifier` が返す `AccessToken.resource` を `resource_server_url` と URL として比較し（大文字小文字・デフォルトポート・末尾スラッシュの差は無視）、不一致または `None` なら WARNING ログを出して認証失敗（未知トークンと同じ 401）。
- `FastMCP.sse_app()` / `streamable_http_app()` が `validate_token_resource` 真のときのみ `resource_server_url` を `BearerAuthBackend` に渡す。
- `RefreshToken.resource: str | None` を追加（リフレッシュ時にバインディングを引き継ぐため）。
- `TokenVerifier.verify_token` の docstring に「`AccessToken.resource` にトークンの発行先（RFC 8707 resource indicator / `aud`）を設定すること」を追記。
- examples（`simple-auth`、`oauth_server` snippet）は `resource_server_url` を `http://127.0.0.1:8000/mcp` に変更し `validate_token_resource=True` を設定。`simple-auth` の `token_verifier.py` は introspection 結果の `aud` を `resource` に載せるよう修正。

**変更前 / 変更後**

- 前: Bearer ミドルウェアはトークンが「このサーバー向けに発行されたか」を確認しない。確認は各 `TokenVerifier` 任せ。
- 後: `validate_token_resource=True` なら、`resource` が `resource_server_url` と一致するトークンだけを受け付ける。未指定なら警告付きで従来通り。

**利用者への影響**

- 破壊的変更なし。ただし `resource_server_url` を設定しているサーバーでは `DeprecationWarning` が出るので、`True` か `False` を明示する。
  - 認可サーバーがクライアントの `resource` パラメータをトークンに紐付ける（MCP クライアントは常に送る）なら `True`。`resource_server_url` はクライアントが接続する正確な URL にする。
  - Auth0 の API identifier や Entra のアプリケーション ID のように独自 audience を使う場合は `False` にし、verifier 側で `aud` を検証する。
- 独自 `TokenVerifier` を `True` で使う場合は `AccessToken.resource` を必ず埋める必要がある（未設定だと全トークンが 401 になる）。`aud` がリストなら `resource_server_url` に等しい要素を入れる。

## 移行チェックリスト（1.29.x → 1.30.0）

1. クライアント: MCP エンドポイント URL がリダイレクト先そのものになっているか確認。別オリジンへのリダイレクトがあれば URL を直す。`httpx.AsyncClient(follow_redirects=True)` は不要。
2. サーバー（Streamable HTTP・ステートフル）: 独自クライアントが GET ストリームなしで 30 分以上間を空ける運用なら `session_idle_timeout` を調整。高負荷環境では `max_sessions` を見直す。
3. OAuth クライアント: 認可サーバーの metadata `issuer` が well-known URL の元と一致しているか確認。M2M プロバイダには `issuer=` を渡す。
4. OAuth サーバー: `AuthSettings(validate_token_resource=True|False)` を明示し、`True` なら `TokenVerifier` が `AccessToken.resource` を返すようにする。
5. テストで `filterwarnings = error` にしている場合、上記 2 つの `DeprecationWarning` に対応する。
