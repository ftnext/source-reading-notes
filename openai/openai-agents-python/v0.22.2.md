## 比較元の決定根拠

- リリースノート末尾の **Full Changelog** リンクが `compare/v0.22.1...v0.22.2` を指している
- `git for-each-ref --sort=-creatordate refs/tags` で v0.22.2 (2026-09-09) の直前タグは v0.22.1 (2026-09-08)。どちらも `main` 上にあり、メンテナンスブランチは無い
- `git merge-base --is-ancestor v0.22.1 v0.22.2` が真。`v0.22.1..v0.22.2` は 5 コミットで、リリースノートの全 5 項目（What's Changed 3 件 + Documentation & Other Changes 2 件）がこの範囲のコミットと 1 対 1 に対応する（翻訳ドキュメント再生成コミット `544b8b03` はリリースノートには現れないがこの範囲に含まれる）
- `pyproject.toml` の `version` は `0.22.1` → `0.22.2`

以上より比較元は v0.22.1 で一意に決まる。

## 全体の要点

小規模なパッチリリース。差分は 94 ファイル (+5,632 / -3,563) だが、`src/` は 7 ファイル (+409 / -58) のみで、残りはテスト、ドキュメント（`docs/ja|ko|zh` の翻訳再生成 58 ファイルを含む）、公開 API 契約のスナップショット。

1. **新機能 1 件**: `ImageGenerationTool` に新しい画像生成モデル・品質オプションを型付きで渡せる `ImageGenerationToolConfig` を追加（#4932）
2. **バグ修正 2 件**
   - `UnixLocal` サンドボックスのファイル API に対するシンボリックリンク差し替え競合（TOCTOU）を防止。セキュリティ強化（#4931）
   - `OpenAIResponsesCompactionSession.pop_item()` 後に古い response ID チェーンを再利用しないよう修正（#4934）
3. **ドキュメント**: v0.22.1 で入った挙動変更・新機能をドキュメントに反映（#4577）。SDK 本体の挙動変更は無い
4. 破壊的変更は宣言されていない。[docs/release.md](https://github.com/openai/openai-agents-python/blob/v0.22.2/docs/release.md) の "Breaking change changelog" にも 0.22.2 の項は無い。ただし `ls(..., user=...)` / `write(..., user=...)` の実装方式が変わり、新たに「システムの python3 への sudo アクセス」が前提になった点は実行環境によって影響し得る（後述）

以下 `[差分]` はソース差分から確認した事実、`[PR]` は PR 本文の記述、`[推測]` はそこから読み取れる範囲の推測。

## 1. feat: 現行の画像生成ツールオプションのサポート（#4932）

- PR: https://github.com/openai/openai-agents-python/pull/4932
- コミット: https://github.com/openai/openai-agents-python/commit/2b5057f693b8d718f541c05c7c38b8a7a012662d
- 分類: **新機能（公開 API 追加）**
- 主な差分: [`src/agents/tool.py`](https://github.com/openai/openai-agents-python/blob/v0.22.2/src/agents/tool.py)、`src/agents/__init__.py`、`src/agents/models/openai_responses.py`、`examples/tools/image_generator.py`

### 何が変わったか

`ImageGenerationTool.tool_config` の型が、OpenAI Python SDK 由来の `ImageGeneration`（`openai.types.responses.tool_param`）だけでなく、Agents SDK 自身が定義する TypedDict **`ImageGenerationToolConfig`** も受け付けるようになった。`ImageGenerationToolConfig` は `agents` トップレベルから export される（`__init__.py` の `__all__` に追加）[差分]。

```python
class ImageGenerationToolConfig(TypedDict, total=False):
    type: Required[Literal["image_generation"]]
    action: Literal["generate", "edit", "auto"]
    background: Literal["transparent", "opaque", "auto"]
    input_fidelity: Literal["high", "low"] | None
    input_image_mask: _ImageGenerationInputImageMask
    model: str
    moderation: Literal["auto", "low"]
    output_compression: int
    output_format: Literal["png", "webp", "jpeg"]
    partial_images: int
    quality: Literal["low", "medium", "high", "xhigh", "max", "auto"]
    size: str
```

ポイントは `quality` に **`"xhigh"` / `"max"`** が入り、`model` が任意の `str`、`size` も任意の `str` になっていること。上流の `openai` パッケージの型定義が API に追いついていない場合でも、`gpt-image-2.5-sunburst` / `gpt-image-2.5-flare` や `quality="xhigh"` を **`cast` 無しで** 型チェックを通せる[PR][差分]。

型チェッカ向けの細工も入っている[差分]:

- `tool_config` は `TYPE_CHECKING` 時だけディスクリプタ Protocol (`_ImageGenerationToolConfigField`) として宣言され、読み出しは `ImageGenerationToolConfig`、代入は `ImageGenerationToolConfig | ImageGeneration` を許す。これで既存コードの再代入や `tool.tool_config["quality"] = ...` のような添字更新の型付けが壊れない
- `__init__` も `TYPE_CHECKING` 時のみ `tool_config: ImageGenerationToolConfig | ImageGeneration` のシグネチャを宣言
- ランタイムは従来どおり素の `@dataclass`
- `Converter`（`openai_responses.py`）側は `return tool.tool_config, None` → `return cast(ResponsesToolParam, tool.tool_config), None` に変更。**設定はそのまま Responses API へ転送される**ので、モデル固有のサポート有無は API 側が検証する[差分][PR]

なお PR レビュー（Codex bot, P2 指摘）では、当初 `tool_config: Any` + `dict[str, Any]` の overload だったため `{"type": "image_generaton"}` のようなタイポも通ってしまう点が指摘され、TypedDict で `type` を `Required[Literal["image_generation"]]` に固定する現在の形に修正されている[PR コメント]。

### 変更前と変更後の挙動

| | 変更前 (v0.22.1) | 変更後 (v0.22.2) |
| --- | --- | --- |
| 型注釈 | `tool_config: ImageGeneration`（上流 SDK の TypedDict） | `ImageGenerationToolConfig` も可。読み出し型は `ImageGenerationToolConfig` |
| `quality="xhigh"` / `"max"` | 上流の型に無ければ型エラー。`cast` や `# type: ignore` が必要 | 型チェックを通る |
| 新モデル名 (`model="gpt-image-2.5-flare"` 等) | 上流の `Literal` に無ければ型エラー | `model: str` なので通る |
| ランタイム挙動 | 設定を Responses API へそのまま転送 | **同じ**（転送内容は変わらない） |

**ランタイム挙動の変更は無い**（設定は以前も未検証のまま転送されていた）。純粋に型付けと公開 API の追加[差分]。

### 利用者への影響と使い方

型チェック（mypy / Pyright）を使って画像生成ツールを設定している場合の記述量が減る。新旧どちらの書き方も引き続き動作する。

```python
from agents import Agent, ImageGenerationTool, ImageGenerationToolConfig

image_config: ImageGenerationToolConfig = {
    "type": "image_generation",
    "model": "gpt-image-2.5-flare",
    "action": "generate",
    "size": "1536x864",
    # GPT Image 2.5 系では xhigh / max でより高品質
    "quality": "low",
}

agent = Agent(
    name="Image generator",
    instructions="Always use the image generation tool when the user asks for a new image.",
    tools=[ImageGenerationTool(tool_config=image_config)],
)
```

（`examples/tools/image_generator.py` の更新後の内容とほぼ同じ[差分]）

移行時の注意:

- 既存の `ImageGenerationTool(tool_config={"type": "image_generation", "quality": "low"})` はそのまま有効。**破壊的変更ではない**
- ただし `tool_config` を厳密に `ImageGeneration` 型として受け渡していたユーザーコード（`def f(c: ImageGeneration)` に `tool.tool_config` を渡す等）は、読み出し型が `ImageGenerationToolConfig` に変わるため型チェッカが警告する可能性がある[推測]
- `model` / `size` は `str` なので **タイポは型チェックで検出できない**。誤りは API エラーとして返る
- 公開 API 契約テストの許可リストにも登録済み（`tests/fixtures/released_api_contract_policy.json`、`tests/fixtures/released_api_contract.json`）[差分]
- リリース時点で `docs/` への記載は無い。このリポジトリの方針（未リリース機能の docs は別 PR）による[推測]

## 2. fix(sandbox): UnixLocal ファイル API のシンボリックリンク競合を防止（#4931）

- PR: https://github.com/openai/openai-agents-python/pull/4931
- コミット: https://github.com/openai/openai-agents-python/commit/e3a03edf186b9a2513d20dc79e6c585d3433272a
- 分類: **バグ修正（セキュリティ強化 / 内部実装の大幅な入れ替え）**
- 主な差分: `src/agents/sandbox/sandboxes/_unix_local_file_ops.py`（新規 177 行）、`_unix_local_files.py`（新規 50 行）、[`unix_local.py`](https://github.com/openai/openai-agents-python/blob/v0.22.2/src/agents/sandbox/sandboxes/unix_local.py)（+154/-53）

### 何が変わったか

`UnixLocalSandboxSession` のファイル API（`ls` / `mkdir` / `rm` / `read` / `write`、および同じ API を経由する `apply_patch`）における **TOCTOU（Time-of-check to time-of-use）競合**を修正した。

問題: パスを検証（ワークスペース root や `extra_path_grants` の範囲内かのチェック）してから実際のファイル操作を行うまでの間に、サンドボックス内のプロセスがそのパスをシンボリックリンクへ差し替えると、操作がワークスペース外へ到達し得た[PR]。

対策[差分]:

- 新規 `_FileOps`（`_unix_local_file_ops.py`）が **ファイルディスクリプタ相対**の操作を提供。`/` から 1 要素ずつ `os.open(part, O_SEARCH|O_DIRECTORY|O_NOFOLLOW, dir_fd=fd)` で降りていき、途中でシンボリックリンクを辿らない。ファイル本体も `O_NOFOLLOW` 付きで開く
  ```python
  _DIRECTORY_FLAGS = os.O_RDONLY | os.O_DIRECTORY | os.O_NOFOLLOW
  _TRAVERSE_FLAGS = (
      getattr(os, "O_SEARCH", getattr(os, "O_PATH", os.O_RDONLY)) | os.O_DIRECTORY | os.O_NOFOLLOW
  )
  ```
- `_UnixLocalFiles`（`_unix_local_files.py`）が manifest の root と grant を **一度 `resolve()` した実パスとしてピン留め**し、以後 manifest が更新されてもエイリアスは固定のまま再認可する（`configure()` は既知の path をキャッシュから再利用）
- `unix_local.py` の各操作を置き換え: `os.scandir(normalized)` → `self._files.directory(...)` の fd 経由、`normalized.mkdir(...)` → `self._files.mkdir(...)`、`shutil.rmtree` / `unlink` → `self._files.rm(...)`、`open("rb"/"wb")` → `self._files.read/write(...)`
- `ls` の結果の `path` が `entry.path` から `str(normalized / entry.name)` に変更（正規化済み絶対パスで返る）
- **user 指定の操作も race-safe に**: 従来 `ls(path, user=...)` は基底クラスの shell 実装、`write(path, stream, user=...)` は `sh -c 'mkdir -p ... && cat > "$1"'` を使っていたが、これらは confinement が無く同じ攻撃が成立した（Codex レビューの P1 指摘）[PR コメント]。修正後は `_run_file_operation_as_user()` が **`python3 -I -S -c <ワーカーソース>`** を対象ユーザーで起動し、`ls` は JSON を stdout に返し `write` は stdin から受け取る。ワーカーのソースは import 時に `inspect.getsource(_unix_local_file_ops)` でキャプチャされる（セッションがワークスペース内のファイルを書き換えても、実行されるのはインストール済み SDK のコード）[差分]

### 変更前と変更後の挙動

| | 変更前 (v0.22.1) | 変更後 (v0.22.2) |
| --- | --- | --- |
| パス検証後の symlink 差し替え | ワークスペース外のファイルを読み書きし得た | 各階層を `O_NOFOLLOW` で辿るため、差し替えられた symlink は辿らない（エラーになる） |
| `ls(..., user=...)` の実装 | `ls` 相当の shell 実行（基底クラス） | 対象ユーザーで `python3 -I -S` のワーカーを実行し JSON を解析 |
| `write(..., user=...)` の実装 | `sh -c 'mkdir -p "$(dirname "$1")" && cat > "$1"'` | 同ワーカーの `write` オペレーション |
| `ls` の `path` フィールド | `os.scandir` の `entry.path` | 正規化済み絶対パス `str(normalized / entry.name)` |
| 正当な symlink | 利用可能 | 利用可能（維持）[PR] |
| 他のサンドボックスバックエンド | — | 変更なし[PR] |

### 利用者への影響

- **セキュリティ修正**。`UnixLocalSandboxClient` を使い、サンドボックス内で信頼できないコードを走らせている場合は v0.22.2 への更新が望ましい。ただし docs にもあるとおり Unix-local はもともとホストプロセスとしてコマンドを実行する軽量バックエンドであり、強い隔離が必要なら Docker やホスト型サンドボックスを使うべき、という前提は変わらない
- **新しい前提条件**: user 指定の listing / write は「システムの `python3` とその標準ライブラリへの sudo アクセス」を必要とする（クラス docstring に明記された）[差分]。`python3` が sudo 経由で見えない環境で `ls(..., user=...)` / `write(..., user=...)` を使っていた場合、失敗するようになる可能性がある[推測]
- API シグネチャ、エラー型（`ExecNonZeroError` / `WorkspaceArchiveWriteError` / `WorkspaceReadNotFoundError`）、ストリーム所有権、ユーザー権限チェック、Python 3.10 互換は維持[PR][差分]
- `ls` の戻り値の `path` が正規化済み絶対パスになるため、相対パスや非正規化パスを渡していた場合に文字列が変わる点は注意[差分]
- テストは `tests/sandbox/test_unix_local_file_io.py`（419 行）と `test_unix_local_user_file_io.py`（332 行）が新規追加

## 3. fix(sessions): pop 後に compaction の response チェーンをリセット（#4934）

- PR: https://github.com/openai/openai-agents-python/pull/4934（Fixes #4867）
- コミット: https://github.com/openai/openai-agents-python/commit/25af629b3c877ba3d0e95189141bb636b21167a5
- 分類: **バグ修正（挙動変更を含む）**
- 差分: [`src/agents/memory/openai_responses_compaction_session.py`](https://github.com/openai/openai-agents-python/blob/v0.22.2/src/agents/memory/openai_responses_compaction_session.py) の `pop_item()` に 7 行追加のみ

### 何が変わったか

`OpenAIResponsesCompactionSession.pop_item()` がローカル履歴からアイテムを削除した後も、保持していた response ID チェーンをそのまま使い続けていた。削除済みの履歴を指す **stale な `previous_response_id`** で compaction が走ると、サーバー側の履歴と手元の履歴が食い違う。

修正は、既存の mutation ロック内で以下 3 つを `None` にリセットする[差分]:

```python
self._response_id = None
self._deferred_response_id = None
self._last_unstored_response_id = None
```

リセットするのは 2 経路:

1. `pop_item()` が成功して実際にアイテムを取り除いたとき（`if popped:`）
2. `underlying_session.pop_item()` が例外／`asyncio.CancelledError` を投げたとき — **削除自体は commit 済みで ack だけ失敗した可能性がある**ため、フェイルセーフにリセットする（追加コメント: `# The deletion may have committed before acknowledgement failed.`）

履歴が空で pop が何もしなかった場合（`popped` が falsy かつ例外なし）は、チェーン状態を維持する[差分][PR]。

### 変更前と変更後の挙動

| | 変更前 (v0.22.1) | 変更後 (v0.22.2) |
| --- | --- | --- |
| pop 成功後の compaction | 保持済みの `previous_response_id` を再利用（削除済み履歴を指す可能性） | チェーンをリセット。`previous_response_id` 方式の compaction には response ID の明示指定が必要 |
| pop が例外／キャンセルで終わった後 | チェーンを保持 | 同様にリセット（削除が commit 済みかもしれないため） |
| pop が空振り（履歴なし） | チェーン保持 | チェーン保持（変更なし） |
| 公開シグネチャ・保存フォーマット | — | 変更なし[PR] |

### 利用者への影響

- `OpenAIResponsesCompactionSession` で `pop_item()`（例: 直前のやり取りの取り消し）を使っていた場合の不整合が解消される
- pop 後は `previous_response_id` ベースの compaction が「response ID を明示的に渡さない限り」実行されなくなる。残っているローカル履歴に対する **input ベースの compaction は引き続き利用可能**[PR]
- 新しい response ID（次のモデル応答）が入れば compaction は再び有効になる[PR のテスト説明]
- 同じ issue #4867 のうち `clear_session` 側の修正（#4865）は別対応で、この PR には含まれない[PR]

## 4. docs: v0.22.1 の挙動更新をドキュメント化（#4577）
